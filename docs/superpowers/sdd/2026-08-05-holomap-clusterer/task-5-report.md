`registerHooks` resolve fallback (`.js` → `.ts` only on

## Deviations from the brief, and why

1. **Added `npm/wasm/package.json` (`{"type":"commonjs"}`)**, and one block
   in `scripts/build-wasm.sh` to regenerate it on every build. Not in the
   brief's Step 1 text. Required: `npm/package.json` declares `"type":
   "module"`, but `wasm-bindgen --target nodejs` emits CommonJS glue
   (`exports.foo = ...`). Without a directory-scoped override, Node treats
   `npm/wasm/*.js` as ESM by nearest-package.json lookup and throws
   `exports is not defined in ES module scope` the instant `WasmClusterer`
   tries to load it — this isn't a corner case, it's the very first
   `require()` call. Scoping the override to `npm/wasm/` (rather than
   changing the whole package to CJS) keeps everything else as-is.

2. **`worker-smoke.test.ts`'s `execArgv`** gained `'--import', LOADER`
   pointing at a new `npm/test/ts-extension-loader.mjs`, instead of the
   brief's bare `['--experimental-strip-types']`. Required: confirmed via a
   minimal `/tmp` repro and the Node docs (fetched live) that
   `--experimental-strip-types` never remaps a `.js` import specifier to a
   sibling `.ts` file — "file extensions are mandatory... `import
   './file.ts'`, not `import './file.js'`" — so the brief's literal worker
   code, importing `../src/index.ts` which internally imports `./types.js`,
   cannot resolve under raw node on this Node version (v26.2.0) no matter
   what `wasm-clusterer.ts` does. The loader is a generic one-line
   extension-fallback resolve hook (`registerHooks`, the current
   non-deprecated in-thread API) — it does not special-case this package,
   doesn't touch `src/`'s import style (which must keep `.js` specifiers for
   `tsc`'s NodeNext output and for vitest's own resolver), and doesn't
   change any assertion in the test.

3. **Brief's Step 3/5 says "4 tests" for `wasm-clusterer.test.ts`**; the
   verbatim test file specified in Step 2 produces 8 (an `it.each` with 4
   seed cases inside one of five `it` blocks). Used the file exactly as
   given — flagging this as a stale count in the brief's prose, not a
   change I made.

Everything else — `npm/src/wasm-clusterer.ts`, `npm/src/index.ts`'s export
line, `npm/test/wasm-clusterer.test.ts`, `npm/test/worker-smoke.test.ts`
(other than the `execArgv` line), `scripts/build-wasm.sh`'s core command
block, and the `build:wasm` script entry — is verbatim from the brief.

### Investigated: is `require.cache` observable from the vitest ESM context?

Yes, and shared correctly. Verified directly before writing the test:

```
$ node -e "
const { createRequire } = require('node:module');
const req1 = createRequire('/tmp/tstest/src/a.js');
const req2 = createRequire('/tmp/tstest/other.js');
console.log('same cache object:', req1.cache === req2.cache);
console.log(typeof req1.cache);
"
same cache object: true
object
```

`createRequire()` from any file returns a require function whose `.cache`
is the process's single shared `Module._cache` — not a per-call cache — so
a `createRequire` in the test file observes exactly what `wasm-clusterer.ts`'s
own `createRequire` populates. Vitest's default `isolate: true` (thread pool,
fresh module registry per test file) keeps this from leaking across other
test files, so no ordering dependency on `wasm-clusterer.test.ts` or
`worker-smoke.test.ts` having already run.
